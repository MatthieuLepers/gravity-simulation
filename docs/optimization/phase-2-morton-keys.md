# Phase 2 — Morton key generation

## Implementation

- The existing `HilbertCurveShader.wgsl` entry point and texture names remain unchanged to avoid breaking callers. The key generated by the shader is a **3D Morton code (Z-order curve)**, not a Hilbert index.
- Each coordinate is normalized against the configured cube `[-100, 100]`, quantized to a cell in a `1024 × 1024 × 1024` grid, then clamped to the grid bounds.
- Each axis contributes 10 bits. The interleaved key therefore uses 30 bits and fits in `u32`.
- The `rg32uint` output texture stores the Morton key in R and the original particle index in G. Both values remain integers; no float bit-casting is used.
- Grid size and bounds are configured in `HilbertCurveKernel.ts` and passed as shader overrides.

## Reference cases

The CPU reference for validation is: normalize each coordinate using `(p - min) / (max - min)`; calculate `floor(normalized * 1024)`; clamp to `[0, 1023]`; interleave the low 10 bits in X/Y/Z order (X at bit positions 0, 3, 6…; Y at 1, 4, 7…; Z at 2, 5, 8…).

| Input position | Quantized cell | Expected Morton key |
| --- | --- | --- |
| `(-100, -100, -100)` | `(0, 0, 0)` | `0x00000000` |
| `(-99.8046875, -100, -100)` | `(1, 0, 0)` | `0x00000001` |
| `(-100, -99.8046875, -100)` | `(0, 1, 0)` | `0x00000002` |
| `(-100, -100, -99.8046875)` | `(0, 0, 1)` | `0x00000004` |
| `(100, 100, 100)` | `(1023, 1023, 1023)` | `0x3fffffff` |
| `(-200, -200, -200)` | `(0, 0, 0)` | `0x00000000` |
| `(200, 200, 200)` | `(1023, 1023, 1023)` | `0x3fffffff` |

The original index written beside each key must equal the invocation index, including for duplicate positions and positions clamped to the same boundary cell.

## Validation checklist

- [ ] Build and lint pass.
- [ ] Compare GPU output against a CPU reference for the table above.
- [ ] Include negative coordinates, points outside the configured cube, identical positions, and points on both bounds.
- [ ] Verify every output pair is `(Morton key, original particle index)`.
- [ ] Confirm the simulation still runs and that the key texture dimensions cover all particles.

## Scope and limitations

This phase only generates keys and retains the source index. It does not implement or repair radix sorting, reorder particles, or change force calculations. Clamping deliberately maps all positions beyond a face to that face's boundary cell; if the simulation's world grows beyond these fixed bounds, the constants must be adjusted. Morton ordering improves spatial locality statistically, but nearby keys are not a guarantee that every pair of spatially close particles will be adjacent. Morton keys alone also do not preserve the full long-range Newtonian gravity calculation.
